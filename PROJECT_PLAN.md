# План разработки информационной системы предприятия автосервиса

## 1. Назначение проекта

Разработать desktop-приложение для предприятия автосервиса, которое хранит данные в реляционной базе данных SQLite и позволяет сотруднику выполнять основные операции с клиентами, автомобилями клиентов, услугами, запчастями, заказ-нарядами и платежами.

Проект должен удовлетворять требованиям курсового проекта по дисциплине «Проектирование информационных систем»:

- выполнить анализ предметной области и информационных процессов;
- спроектировать нормализованную реляционную базу данных;
- реализовать создание, заполнение, изменение, удаление и индексирование данных;
- разработать desktop-приложение для работы с базой данных;
- реализовать не менее пяти типов SQL-запросов: выборку, поиск, группировку, изменение и удаление;
- реализовать хотя бы один динамический запрос;
- подготовить отчетную документацию, схемы, диаграммы, скриншоты и руководство пользователя;
- подготовить устанавливаемую сборку приложения для демонстрации.

## 2. Технологический стек

Конфигурация строится по проверенному подходу проекта информационной системы инвестиционной компании, но адаптируется к предметной области автосервиса.

## 4. Пользователи и сценарии

### 4.1. Администратор

- управляет сотрудниками;
- просматривает и редактирует справочники;
- контролирует целостность данных;
- формирует общие отчеты.

### 4.2. Мастер-приемщик

- регистрирует клиентов;
- добавляет автомобили клиентов;
- открывает заказ-наряды;
- регистрирует расход запчастей и платежи;
- ищет заказ-наряды за выбранный период;
- формирует отчет по конкретному клиенту.

### 4.3. Механик

- просматривает услуги, запчасти и заказ-наряды;
- анализирует историю обслуживания автомобилей;
- получает агрегированные показатели по клиентам и услугам;
- формирует отчеты за период.

## 5. Информационные процессы

1. Сотрудник создает карточку клиента и назначает ответственного мастера-приемщика.
2. Для клиента добавляется один или несколько автомобилей.
3. В справочник добавляются услуги и их текущие цены, а также запчасти.
4. Сотрудник открывает заказ-наряд на обслуживание автомобиля клиента.
5. Система проверяет, что автомобиль находится в активном состоянии.
6. К заказ-наряду добавляется расход необходимых запчастей.
7. По завершении работ регистрируется платеж по заказ-наряду.
8. Новые цены услуг не изменяют уже созданные заказ-наряды, только новые.
9. Пользователь применяет фильтры и получает список заказ-нарядов или агрегированный отчет.

## 6. Проектирование базы данных

Поля:

- `id` — первичный ключ;
- `last_name`;
- `first_name`;
- `middle_name` — допускает NULL;
- `position`;
- `phone`;
- `email`;
- `is_active`;
- `created_at`.

Ограничения:

- уникальный `email`;
- обязательные имя, фамилия и должность.

### 6.2. Таблица `Client`

Поля:

- `id` — первичный ключ;
- `advisor_id` — внешний ключ на `Employee` (ответственный мастер-приемщик);
- `last_name`;
- `first_name`;
- `middle_name` — допускает NULL;
- `phone`;
- `email`;
- `registration_date`;
- `status`;
- `search_name`;
- `created_at`;
- `updated_at`.

Ограничения:

- уникальный `email`;
- статус из фиксированного набора: `ACTIVE`, `BLOCKED`, `ARCHIVED`.

### 6.3. Таблица `Vehicle`

Поля:

- `id` — первичный ключ;
- `client_id` — внешний ключ на `Client`;
- `make`;
- `model`;
- `year`;
- `license_plate`;
- `vin`;
- `status`;
- `registered_at`;
- `retired_at` — допускает NULL.

Ограничения:

- уникальный `license_plate`;
- уникальный `vin`;
- статус: `ACTIVE`, `SOLD`, `BLOCKED`.

### 6.4. Таблица `ServiceCategory`

Поля:

- `id` — первичный ключ;
- `name`;
- `description` — допускает NULL.

Примеры: техническое обслуживание, ремонт двигателя, ремонт ходовой, кузовной ремонт, диагностика, шиномонтаж.

### 6.5. Таблица `Service`

Поля:

- `id` — первичный ключ;

- `code`;
- `name`;
- `is_active`;
- `created_at`.

Ограничения:

- уникальный `code`;
- обязательные название, категория.

### 6.6. Таблица `ServicePrice`

Поля:

- `id` — первичный ключ;
- `service_id` — внешний ключ на `Service`;
- `price_date`;
- `price`.

Ограничения:

- цена больше нуля;
- уникальная пара `service_id + price_date`.

### 6.7. Таблица `Part`

Поля:

- `id` — первичный ключ;
- `sku`;
- `name`;
- `unit_price`;
- `quantity_in_stock`;
- `is_active`;
- `created_at`.

Ограничения:

- уникальный `sku`;
- цена больше нуля;
- остаток на складе неотрицательный.

### 6.8. Таблица `WorkOrder`

Поля:

- `id` — первичный ключ;
- `vehicle_id` — внешний ключ на `Vehicle`;
- `service_id` — внешний ключ на `Service`;
- `mechanic_id` — внешний ключ на `Employee`;
- `status`;
- `open_date`;
- `quantity`;
- `unit_price`;
- `discount`;
- `comment` — допускает NULL;
- `created_at`.

Ограничения:

- статус: `NEW`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`;
- количество и цена больше нуля;
- скидка неотрицательная;
- заказ-наряд нельзя открыть на автомобиль, не находящийся в статусе `ACTIVE`.

### 6.9. Таблица `PartUsage`

Поля:

- `id` — первичный ключ;
- `work_order_id` — внешний ключ на `WorkOrder`;
- `part_id` — внешний ключ на `Part`;
- `usage_date`;
- `amount`;
- `discount_amount`.

Ограничения:

- сумма больше нуля;
- скидка неотрицательна и не превышает сумму.

### 6.10. Таблица `Payment`

Поля:

- `id` — первичный ключ;
- `work_order_id` — внешний ключ на `WorkOrder`;
- `payment_date`;
- `amount`;
- `discount_amount`.

Ограничения:

- сумма больше нуля;
- скидка неотрицательна и не превышает сумму.

### 6.11. Расчет расходов клиента

Сводка расходов клиента не хранится как отдельная изменяемая таблица. Она рассчитывается SQL-запросом как сумма чистых платежей по заказ-нарядам, сгруппированная по клиенту через принадлежащие ему автомобили. Это предотвращает расхождение платежей и агрегатов.

Результат запроса сводки:

- клиент;
- количество автомобилей;
- суммарные платежи.

## 7. Обязательные SQL-запросы

Каждый запрос должен быть представлен в SQLDelight `.sq`-файле, использоваться в интерфейсе и быть описан в пояснительной записке.

### Запрос 1. Выборка

Получение списка клиентов вместе с назначенным мастером-приемщиком и количеством автомобилей.

Критерий приемки: список отображается в интерфейсе и корректно включает клиентов без автомобилей.

### Запрос 2. Поиск

Поиск клиентов по части фамилии, имени, телефону или email.

Критерий приемки: поиск регистронезависимый, пустая строка возвращает общий список.

### Запрос 3. Группировка

Расчет суммарных платежей с группировкой по клиентам через их автомобили.

Критерий приемки: для каждого клиента выводится количество автомобилей и суммарные платежи.

### Запрос 4. Добавление данных

Добавление клиента, автомобиля, услуги, цены, запчасти, заказ-наряда, расхода запчасти и платежа.

Критерий приемки: данные сохраняются после перезапуска приложения.

### Запрос 5. Изменение данных

Редактирование данных клиента и текущего состояния услуги.

Критерий приемки: изменения сразу отображаются и сохраняются в SQLite.

### Запрос 6. Удаление данных

Удаление ошибочно зарегистрированного заказ-наряда с подтверждением пользователя.

Критерий приемки: после удаления пересчитываются отчеты.

Для сущностей с зависимостями предпочтительно архивирование вместо физического удаления. Физическое удаление заказ-наряда запрещается, если у него есть расходы запчастей или платежи.

### Запрос 7. Динамический запрос

Фильтрация заказ-нарядов по произвольной комбинации параметров:

- автомобиль;
- клиент;
- услуга;
- статус;
- начальная дата;
- конечная дата;
- минимальная сумма;
- максимальная сумма.

Критерий приемки: любой фильтр необязателен; одновременно могут быть заданы несколько фильтров; изменение фильтра обновляет результат без формирования SQL строковой конкатенацией в UI.

### Дополнительные отчеты

- оборот по месяцам (заказ-наряды и расход запчастей);
- выручка по категориям услуг;
- крупнейшие клиенты по суммарным платежам;
- история цены выбранной услуги;
- остатки запчастей на складе;
- количество заказ-нарядов по статусам.

## 8. Архитектура приложения

### 8.1. Пакеты

```text
me.autoservice
├── app
├── domain
│   ├── model
│   ├── port
│   └── service
├── persistence
│   ├── mapper
│   └── db
├── report
└── ui
    ├── component
    ├── dashboard
    ├── client
    ├── employee
    ├── vehicle
    ├── service
    ├── part
    ├── workorder
    ├── report
    └── theme
```

### 8.2. Ответственность слоев

- `domain/model` — модели и значения предметной области без Compose и SQLDelight;
- `domain/port` — интерфейсы репозиториев;
- `domain/service` — правила регистрации заказ-нарядов и расчета показателей;
- `persistence` — SQLite, SQLDelight, преобразование записей БД в доменные модели;
- `ui` — состояние экранов, обработка действий и Compose-компоненты;
- `app` — запуск приложения, создание базы данных и связывание зависимостей;
- `report` — модели и преобразования для отчетов.

### 8.3. Правила зависимостей

- доменный слой не зависит от Compose, SQLDelight и Swing;
- UI использует доменные модели и интерфейсы;
- persistence реализует доменные интерфейсы;
- SQLDelight-записи не передаются напрямую в UI;
- бизнес-правила не размещаются внутри Composable-функций;
- операции ввода-вывода выполняются вне UI-потока через coroutines.

## 13. Риски

### Риск: слишком большой объем

Мера: сначала реализовать обязательные сущности, SQL-запросы и табличные отчеты; экспорт и сложные графики оставить дополнительными задачами.

### Риск: несоответствие требованиям преподавателя

Мера: до реализации уточнить, допустимы ли Kotlin, Compose Desktop и SQLite, и показать преподавателю стек и схему БД.

### Риск: некорректный расчет отчетов

Мера: рассчитывать выручку из неизменяемой истории заказ-нарядов и платежей и покрыть расчет интеграционными тестами.

### Риск: проблемы сборки под Windows при разработке на macOS

Мера: заранее проверить MSI на Windows; Compose native distributions обычно собираются для текущей ОС, поэтому финальную MSI-сборку выполнять на Windows или Windows CI.

### Риск: недостаточный объем пояснительной записки

Мера: параллельно сохранять диаграммы, SQL-запросы, решения, результаты тестов и скриншоты, а не писать документацию только после завершения кода.
