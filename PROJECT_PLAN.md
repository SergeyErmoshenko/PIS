# План разработки информационной системы инвестиционной компании

## 1. Назначение проекта

Разработать desktop-приложение для инвестиционной компании, которое хранит данные в реляционной базе данных SQLite и позволяет сотруднику выполнять основные операции с клиентами, инвестиционными счетами, финансовыми инструментами, сделками и портфелями.

Проект должен удовлетворять требованиям курсового проекта по дисциплине «Проектирование информационных систем»:

- выполнить анализ предметной области и информационных процессов;
- спроектировать нормализованную реляционную базу данных;
- реализовать создание, заполнение, изменение, удаление и индексирование данных;
- разработать desktop-приложение для работы с базой данных;
- реализовать не менее пяти типов SQL-запросов: выборку, поиск, группировку, изменение и удаление;
- реализовать хотя бы один динамический запрос;
- подготовить отчетную документацию, схемы, диаграммы, скриншоты и руководство пользователя;
- подготовить устанавливаемую сборку приложения для демонстрации.

## 2. Технологический стек

Конфигурация строится по проверенному подходу проекта Terevo, но адаптируется к предметной области инвестиционной компании.

- Kotlin 2.4.0;
- JVM 21;
- Compose Multiplatform Desktop;
- Material 3;
- SQLite;
- SQLDelight 2.1.0;
- kotlinx.coroutines;
- kotlinx.collections.immutable;
- kotlinx.datetime;
- kotlinx.serialization;
- kotlin-logging и Logback;
- Kotlin Test и JUnit 5;
- Kotest Assertions;

Целевой вариант приложения — Compose Desktop для JVM. Это соответствует требованию desktop-приложения, позволяет собрать MSI для Windows и не требует усложнения проекта отдельными платформенными модулями.

## 4. Пользователи и сценарии

### 4.1. Администратор

- управляет сотрудниками;
- просматривает и редактирует справочники;
- контролирует целостность данных;
- формирует общие отчеты.

### 4.2. Инвестиционный менеджер

- регистрирует клиентов;
- открывает инвестиционные счета;
- регистрирует покупки и продажи;
- просматривает портфели клиентов;
- ищет операции за выбранный период;
- формирует отчет по конкретному клиенту.

### 4.3. Аналитик

- просматривает финансовые инструменты и историю цен;
- анализирует стоимость и структуру портфелей;
- получает агрегированные показатели по клиентам и инструментам;
- формирует отчеты за период.

## 5. Информационные процессы

1. Сотрудник создает карточку клиента и назначает клиентского менеджера.
2. Для клиента открывается один или несколько инвестиционных счетов.
3. В справочник добавляются финансовые инструменты и их текущие цены.
4. Сотрудник регистрирует покупку инструмента на счет клиента.
5. Система проверяет корректность количества, цены и состояния счета.
6. Покупка увеличивает позицию инструмента в портфеле.
7. При продаже система проверяет, что доступного количества достаточно.
8. Продажа уменьшает или закрывает позицию.
9. Новые цены инструментов изменяют расчетную стоимость портфеля.
10. Дивиденды регистрируются как отдельные начисления по счету и инструменту.
11. Пользователь применяет фильтры и получает список операций или агрегированный отчет.

## 6. Проектирование базы данных

### 6.1. Таблица `Employee`

Поля:

- `id` — первичный ключ;
- `last_name`;
- `first_name`;
- `middle_name` — допускает NULL;
- `position`;
- `phone`;
- `email`;
- `is_active`;
- `created_at`.

Ограничения:

- уникальный `email`;
- обязательные имя, фамилия и должность.

### 6.2. Таблица `Client`

Поля:

- `id` — первичный ключ;
- `manager_id` — внешний ключ на `Employee`;
- `last_name`;
- `first_name`;
- `middle_name` — допускает NULL;
- `birth_date`;
- `phone`;
- `email`;
- `passport_number`;
- `registration_date`;
- `status`;
- `created_at`;
- `updated_at`.

Ограничения:

- уникальный `passport_number`;
- уникальный `email`;
- статус из фиксированного набора: `ACTIVE`, `BLOCKED`, `ARCHIVED`.

### 6.3. Таблица `InvestmentAccount`

Поля:

- `id` — первичный ключ;
- `client_id` — внешний ключ на `Client`;
- `account_number`;
- `opened_at`;
- `closed_at` — допускает NULL;
- `status`;
- `currency`.

Ограничения:

- уникальный `account_number`;
- статус: `OPEN`, `CLOSED`, `BLOCKED`;
- в первой версии валюта — `RUB`.

### 6.4. Таблица `InstrumentType`

Поля:

- `id` — первичный ключ;
- `name`;
- `description` — допускает NULL.

Примеры: акция, облигация, фонд.

### 6.5. Таблица `Instrument`

Поля:

- `id` — первичный ключ;
- `type_id` — внешний ключ на `InstrumentType`;
- `ticker`;
- `name`;
- `issuer`;
- `currency`;
- `is_active`;
- `created_at`.

Ограничения:

- уникальный `ticker`;
- обязательные название, тип и валюта.

### 6.6. Таблица `InstrumentPrice`

Поля:

- `id` — первичный ключ;
- `instrument_id` — внешний ключ на `Instrument`;
- `price_date`;
- `price`.

Ограничения:

- цена больше нуля;
- уникальная пара `instrument_id + price_date`.

### 6.7. Таблица `Trade`

Название `Trade` используется вместо `Transaction`, чтобы не конфликтовать с терминологией транзакций базы данных.

Поля:

- `id` — первичный ключ;
- `account_id` — внешний ключ на `InvestmentAccount`;
- `instrument_id` — внешний ключ на `Instrument`;
- `employee_id` — внешний ключ на `Employee`;
- `trade_type`;
- `trade_date`;
- `quantity`;
- `unit_price`;
- `commission`;
- `comment` — допускает NULL;
- `created_at`.

Ограничения:

- тип: `BUY` или `SELL`;
- количество и цена больше нуля;
- комиссия неотрицательная;
- продажа не должна превышать доступный остаток инструмента на счете.

### 6.8. Таблица `Dividend`

Поля:

- `id` — первичный ключ;
- `account_id` — внешний ключ на `InvestmentAccount`;
- `instrument_id` — внешний ключ на `Instrument`;
- `payment_date`;
- `amount`;
- `tax_amount`.

Ограничения:

- сумма больше нуля;
- налог неотрицательный и не превышает сумму.

### 6.9. Представление портфеля

`PortfolioPosition` не требуется хранить как отдельную изменяемую таблицу. Позиция рассчитывается SQL-запросом как сумма покупок минус сумма продаж, сгруппированная по счету и инструменту. Это предотвращает расхождение сделок и остатков.

Результат запроса позиции:

- счет;
- инструмент;
- суммарное количество;
- средняя цена приобретения;
- последняя цена;
- текущая стоимость;
- расчетная прибыль или убыток.

### 6.10. Индексы

Создать индексы:

- `Client(last_name, first_name)`;
- `Client(manager_id)`;
- `InvestmentAccount(client_id)`;
- `Instrument(ticker)` — уникальный;
- `Instrument(type_id)`;
- `InstrumentPrice(instrument_id, price_date)` — уникальный;
- `Trade(account_id, trade_date)`;
- `Trade(instrument_id, trade_date)`;
- `Trade(employee_id)`;
- `Dividend(account_id, payment_date)`.

## 7. Обязательные SQL-запросы

Каждый запрос должен быть представлен в SQLDelight `.sq`-файле, использоваться в интерфейсе и быть описан в пояснительной записке.

### Запрос 1. Выборка

Получение списка клиентов вместе с назначенным менеджером и количеством открытых счетов.

Критерий приемки: список отображается в интерфейсе и корректно включает клиентов без счетов.

### Запрос 2. Поиск

Поиск клиентов по части фамилии, имени, телефону, email или номеру счета.

Критерий приемки: поиск регистронезависимый, пустая строка возвращает общий список.

### Запрос 3. Группировка

Расчет текущей стоимости портфелей с группировкой по клиентам.

Критерий приемки: для каждого клиента выводится количество инструментов и суммарная текущая стоимость.

### Запрос 4. Добавление данных

Добавление клиента, счета, инструмента, цены, сделки и дивиденда.

Критерий приемки: данные сохраняются после перезапуска приложения.

### Запрос 5. Изменение данных

Редактирование данных клиента и текущего состояния финансового инструмента.

Критерий приемки: изменения сразу отображаются и сохраняются в SQLite.

### Запрос 6. Удаление данных

Удаление ошибочно зарегистрированной сделки с подтверждением пользователя.

Критерий приемки: после удаления пересчитываются портфель и отчеты.

Для сущностей с зависимостями предпочтительно архивирование вместо физического удаления. Физическое удаление клиента запрещается, если у него есть счета или сделки.

### Запрос 7. Динамический запрос

Фильтрация сделок по произвольной комбинации параметров:

- клиент;
- счет;
- финансовый инструмент;
- тип сделки;
- начальная дата;
- конечная дата;
- минимальная сумма;
- максимальная сумма.

Критерий приемки: любой фильтр необязателен; одновременно могут быть заданы несколько фильтров; изменение фильтра обновляет результат без формирования SQL строковой конкатенацией в UI.

### Дополнительные отчеты

- оборот покупок и продаж по месяцам;
- самые крупные портфели;
- структура активов по типам инструментов;
- история цены выбранного инструмента;
- начисленные дивиденды по клиенту за период;
- прибыль или убыток по открытым позициям.

## 8. Архитектура приложения

### 8.1. Пакеты

```text
me.investcompany
├── app
├── domain
│   ├── model
│   ├── port
│   └── service
├── persistence
│   ├── mapper
│   └── db
├── report
└── ui
    ├── component
    ├── dashboard
    ├── client
    ├── employee
    ├── account
    ├── instrument
    ├── trade
    ├── portfolio
    ├── report
    └── theme
```

### 8.2. Ответственность слоев

- `domain/model` — модели и значения предметной области без Compose и SQLDelight;
- `domain/port` — интерфейсы репозиториев;
- `domain/service` — правила регистрации сделок и расчета показателей;
- `persistence` — SQLite, SQLDelight, преобразование записей БД в доменные модели;
- `ui` — состояние экранов, обработка действий и Compose-компоненты;
- `app` — запуск приложения, создание базы данных и связывание зависимостей;
- `report` — модели и преобразования для отчетов.

### 8.3. Правила зависимостей

- доменный слой не зависит от Compose, SQLDelight и Swing;
- UI использует доменные модели и интерфейсы;
- persistence реализует доменные интерфейсы;
- SQLDelight-записи не передаются напрямую в UI;
- бизнес-правила не размещаются внутри Composable-функций;
- операции ввода-вывода выполняются вне UI-потока через coroutines.

## 13. Риски

### Риск: слишком большой объем

Мера: сначала реализовать обязательные сущности, SQL-запросы и табличные отчеты; экспорт и сложные графики оставить дополнительными задачами.

### Риск: несоответствие требованиям преподавателя

Мера: до реализации уточнить, допустимы ли Kotlin, Compose Desktop и SQLite, и показать преподавателю стек и схему БД.

### Риск: некорректный расчет портфеля

Мера: рассчитывать остаток из неизменяемой истории сделок и покрыть расчет интеграционными тестами.

### Риск: проблемы сборки под Windows при разработке на macOS

Мера: заранее проверить MSI на Windows; Compose native distributions обычно собираются для текущей ОС, поэтому финальную MSI-сборку выполнять на Windows или Windows CI.

### Риск: недостаточный объем пояснительной записки

Мера: параллельно сохранять диаграммы, SQL-запросы, решения, результаты тестов и скриншоты, а не писать документацию только после завершения кода.
